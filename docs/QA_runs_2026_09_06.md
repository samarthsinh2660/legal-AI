# QA — the run queue, 2026-09-06

A pass over the queue, the worker and the stream, run against the
containerised stack: one API, three workers, Postgres and Neo4j, with real
model calls. Two suites, both re-runnable:

    scripts/qa/run_queue_qa.py     41 cases over HTTP        41/41
    scripts/qa/run_failure_qa.sh   what a process manager does  8/8

Both re-run clean after the speed work later the same day -- 41/41 and 8/8
-- see `docs/SPEED_2026_09_06.md`, which was itself measured with the
timestamps these runs left in `run_events`.

Two things the speed work did to this suite, both worth recording because
neither showed as a failure:

- **A timing change made an assertion pass for the wrong reason.** Case 3
  restarts a killed worker and asserts it does not pick the stranded run
  back up. It waited a fixed 12 seconds -- but a worker now spends ~26
  loading models before it claims anything, so at 12 seconds it had not
  tried. It waits for "worker ready" now. And that wait had to be scoped
  with `docker logs --since`: a restarted container still holds the
  previous session's "worker ready" line, seven of them by the end of the
  day, so an unscoped grep returns instantly on a worker that has not
  begun.
- **Editing the script while it was running corrupted the run.** Bash reads
  a script incrementally from disk, so the edit landed mid-execution and
  the shell resumed at the wrong byte offset (`line 116: would: command not
  found`). The file was fine; only the run was lost. There is a warning at
  the top of it now, and the re-runs were made from a copy.

The point of running them over HTTP against containers rather than in
pytest is that the properties only exist when the API and the worker are
separate processes: a job outliving a request, a stream replaying to a
client that was not there, a worker draining on SIGTERM.

## What it found

### 1. A message of whitespace bought a full research turn

`Field(min_length=1)` counts characters, so `"   \n\t "` passed every bound
the schema declared. It queued a run, titled the thread `"   "`, spent two
model calls, and held the thread's one run slot for the length of it.

The same hole was open on case titles (`NewCaseRequest`,
`UpdateCaseRequest`) and on profile names (`RenameRequest`) — a case or a
person with no visible name, which cannot be found again in a list.

Fixed in `api/utils/fields.py`: one `Text` type that trims and then
refuses what is empty, shared by the three domains. Trimming happens
*before* the length check, so padding cannot smuggle a value past a
ceiling either.

Deliberately **not** applied to passwords: a password may legitimately
begin or end with a space, and stripping one silently changes the
credential.

Covered by `tests/api/threads/test_request_shapes.py`.

### 2. The worker image was missing a dependency the research path needs

One of six concurrent questions failed with
`ModuleNotFoundError: No module named 'bs4'`.

When the corpus comes up short, `agents.supervisor._discover` falls back to
live discovery, which imports `beautifulsoup4` and `bharat-courts`. Both
had been classed as ingest-only when the dependency extras were split —
correct for where the files live, wrong for when they run.

It survived every start-up check because the import is lazy: nothing loads
it until a real question needs it. So the fix is not only moving the two
packages into the `worker` extra, but a **build-time import smoke** in the
worker stage that reaches the lazy path:

```dockerfile
RUN python -c "import worker.loop, ...; build_research_graph(); \
    import legal_ai.tools.judgments, legal_ai.ingestion.judgments.dynamic_search; \
    from bharat_courts.archive.endpoints import SCI_BUCKET"
```

A missing runtime dependency now fails the build instead of one question in
production.

### 3. Deleting a thread mid-run raised a foreign-key violation per step

Deleting a thread cascades its runs and events away. The worker was still
inside the graph, so every write after that hit rows that no longer
existed: a `ForeignKeyViolation` traceback per step, and the run continued
to completion at full price with nowhere to put an answer.

The worker now checks between nodes — the same seam cancellation will use —
and stops when the run is gone. A deleted run is logged at info, not as an
error: it is the reader's own decision, not a failure.

Covered by three cases in `tests/worker/test_research_job.py`.

### 4. A cross-origin reconnect was blocked at the preflight

`Last-Event-ID` is a custom header, so a browser sends an OPTIONS preflight
before the reconnect and refuses to make the request unless the server
names it. The CORS allow-list had `Authorization` and `Content-Type` and
nothing else.

Every deployment is cross-origin — the frontend on `:3001` against the API
on `:8000` locally, Vercel against the API host in production — so resume
would have failed everywhere while looking exactly like a stream that had
gone quiet.

**Nothing in either suite could have caught it.** The client tests mock
`fetch`, so no preflight is ever made; the QA suite uses curl, which does
not make one either. It was found by reading the OPTIONS response against
the running API by hand.

Fixed in `api/main.py`, with a regression test that asserts the preflight
response rather than the request.

### 5. A finished turn flashed "This didn't finish"

Found by reading the state machine rather than by a test. When a run's
stream says `done`, the thread has no active run — but the reply is still
being refetched, so for that moment the last message is a question with
nothing under it, which is exactly the shape of a turn that died.

The screen therefore showed *"This didn't finish. Ask it again below."* on
a turn that had just succeeded, for as long as the refetch took.

Fixed by holding the state back while the messages query is fetching. The
regression test holds the refetch open on purpose so it sits in the gap;
reverting the fix fails it.

### 6. The test suite assumed it was the only consumer of the queue

Several tests enqueue a job and then claim it, to drive the worker function
with exactly the row the API wrote. With a worker container against the
same database, the container claimed some of them first — and then answered
them for real, storing a real answer where the test expected its own fake.
The failure that followed was a wrong assertion about content, which reads
like a bug in the code under test and is not one.

Three fixes, by what each test actually needs:

- The loop tests enqueue a private `kind` that no worker serves — which is
  what the claim query is for in the first place.
- The two that were only checking what `enqueue` wrote now read the row
  instead of racing for it.
- The rest genuinely need the queue to themselves, so
  `tests/worker/conftest.py` races a probe job at session start and exits
  with one sentence — *stop the worker first* — rather than failing
  intermittently three tests later. Detected by racing rather than by
  looking for a local process: a worker on another machine is just as much
  of a problem and there is nothing local to find.

`tests/api` needs no such guard; it was made worker-agnostic by the second
fix, and passes with workers live.

## What passed

**Input the API refuses** — empty, whitespace, non-breaking space, past the
4000-character ceiling; a message at exactly the ceiling and a padded one
both accepted. Unknown thread and unknown run are 404.

**Ownership** — another user cannot post to a thread, read a run, or open
its stream. All 404, never 403: telling a caller a thing exists confirms
the id.

**One run per thread** — a second message while one is running is 409
`run_in_progress`; the first still finishes; a follow-up is accepted once
it is over.

**Replay and resume** — attaching after a run is over replays all of it and
closes; ids are dense from 1; `Last-Event-ID` replays exactly what was
missed; past the end replays nothing; an unreadable or negative header
replays everything, because replaying too much is cheap and losing an event
is not.

**Two watchers, one run** — byte-identical event streams, served through
one Postgres `LISTEN` connection for the whole API process.

**The reader leaves** — connection dropped after one frame; the run
finished and stored its answer anyway.

**The paths that never reach the graph** — small talk finishes in 2.0s,
emits no research steps, and routes `ANSWER`.

**Text that is not ASCII** — a Devanagari question came back
byte-identical.

**Drafting as a second kind** — starts, refuses a second draft with 409,
shows on the thread as `active_run.kind == "draft"`, finishes, and
downloads as a real `.docx` (`PK\x03\x04`).

**A draft with nothing to cite** — reaches a terminal state with a reason
(*"this conversation has not established any law to draft from"*), rather
than hanging or inventing law.

**Deleting a thread mid-run** — the delete succeeds, the run goes with it,
and the API is still healthy afterwards.

### Concurrency

Six questions queued in **0.13s**, answered by three workers in **58.7s**
total. Each thread ended with exactly one question and one reply, and no
run id appeared in two workers' logs — which is the whole of what
`FOR UPDATE SKIP LOCKED` is for.

### Latency

The POST that used to take 30–130 seconds now returns in **17ms**. Steps
arrive on the `NOTIFY`, not on the heartbeat: measured at 22:01:59 and
22:02:08 on a 20-second beat, so neither landed on a boundary.

### What actually limits throughput

Not the queue. Over 45 minutes of this pass, three workers took **62
rate-limited responses** from the model API — 20, 22 and 20 — because they
share one free-tier key.

So a third worker does not buy a third more answers; it buys a third more
requests against the same quota, and the backoff lands on whichever run is
unlucky. Scaling workers is worth doing when the key is paid, or when the
work is not model-bound. Until then one worker is the honest number, and
the queue is what makes the extra ones a `--scale` flag rather than a
project.

## What a process manager does to a run

`scripts/qa/run_failure_qa.sh`, 8/8, one worker:

| | |
|---|---|
| Worker stopped politely mid-run | drains, finishes the run, stores the answer ✓ |
| Job queued with no worker at all | stays `queued`, runs when one returns ✓ |
| Worker `kill -9` mid-run | row stranded at `running` — the known gap |
| Restarting that worker | does **not** pick the stranded run back up |
| API restarted mid-run | the run finishes regardless ✓ |
| Watching through the *fresh* API | replays all 16 frames ✓ |

The last one is the property worth naming: the API that served the replay
had never seen the run start. Any instance can serve any run, because the
state is in the table and not in the process working on it.

The first attempt at case 1 reported a false failure — it stopped the first
worker container rather than the one that had claimed the run, which with
three running is usually the wrong one. The script now finds the owner in
the logs first.

## Two things this pass did not fix

- **A worker killed outright strands its row.** SIGTERM drains — verified —
  but `kill -9` or a lost machine leaves `status = running` with nothing
  coming, and the reader waits on an answer that will not arrive. The
  reaper (`heartbeat_at`, swept) is what closes it.
- **No cancellation.** A reader who has gone still pays for the whole run.
  The between-nodes check added in finding 3 is the seam it will use.

Both are Phase 4 in the reliability architecture, and both are listed in
`docs/TODO.md`.

## Re-run after the model servers went in

41 cases again, 39 passed. Neither failure was the model service:

- **"the draft finishes"** -- that run's research turn came back with no
  evidence-bearing claims, because the model API was throttled, and the
  drafter correctly refused a document it could not cite. Drafting itself
  was verified working on a thread with a real answer in the same session.
  The case now asserts its own precondition, so a thin fixture reports as
  a thin fixture.
- **"drafting raised"** -- a third harness bug of the same family as the
  first two: on a failed download `request()` returned parsed JSON to a
  caller expecting bytes, so `content[:8]` hit a dict and raised
  `KeyError(slice(None, 8, None))`. An error body is now returned as bytes
  to a `raw` caller.

## A later pass, against the product's own promise

The suites above test the plumbing. `scripts/qa/run_grounding_qa.py` tests
the thing the plumbing protects: it asks real questions through the live
system and looks every cited id up in the database.

It found two bugs, both in the honesty of what a reader is told.

**A legal question the planner could make nothing of was told the system
does not do Indian law.** `plan_research` returns no angles for two
different things -- a question that is not law at all, and a legal one with
no researchable issue in it. Both got *"I only research Indian law -- so I
cannot help with that"*, which is true of the first and false of the
second: a reader asking about a section of the Negotiable Instruments Act
was told we do not cover it. Of the two states to collapse into, that was
the wrong one. The reply is now about the question -- *"I could not find a
legal issue in that to research"* -- which is true of both.

**Two of the suite's own assertions passed vacuously.** "No claim without
evidence" is trivially true of an answer with no claims, which is what a
throttled model produces -- so it passed while proving nothing. And the
fabrication check asked about a section that does not exist, which planned
no angles, so nothing was ever generated to check. Both now assert their
own precondition first, and the fabrication check asks something the
planner can work with.

That is the third and fourth time in this project's QA that a test passed
for a reason other than the one it named. The pattern is consistent enough
to state as a rule: **assert that the interesting thing happened before
asserting something about it.**

## Not covered

- **Nobody has watched a reopened thread reattach on a screen.** The
  component is covered by tests against a real SSE stream and the whole
  path was driven through the API, but the browser extension was not
  connected during this pass.
- **Sustained load.** Six concurrent questions is a fan-out check, not a
  load test. Notably, six *pollers* at 5s trip the per-address rate limiter
  at 60 requests a minute — which is the cost the stream removes, and the
  reason the QA suite watches rather than polls.
