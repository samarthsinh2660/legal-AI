# Response speed — findings and options

Quick mode measured at 30-50s, Verified at ~130s. This is a survey of how
production RAG/agent systems cut latency, matched against what our pipeline
already does and does not do. No code changed. Ten searches, sources linked
per section.

## Where our time actually goes

One turn is a fixed LangGraph chain: `document -> context_builder ->
clarification -> research -> analyst -> verification -> draft`, with
`verification -> research` allowed to loop up to `max_verification_passes`
(2). Quick mode runs this chain once; Verified can run `research` and
`analyst` a second time if the first pass left claims unsupported --
`supervisor.py`'s docstring already measured that loop-back as a 4-call,
45-60s cost, which is most of the 80s gap between modes.

Two things in the current code are worth naming because they map directly
onto the findings below:

- `research()`'s `for angle in angles: _search(...)` loop (supervisor.py)
  is sequential per angle. Most questions plan one angle, so this rarely
  bites -- but `max_concurrent_research_units` allows 3, and a 3-angle
  question pays for 3 sequential retrievals today.
- Nothing in `llm/client.py` sets a `thinking_budget`. The model chain is
  already Flash-tier (`gemini-flash-latest` down to `-flash-lite`), which
  is the right family, but an unset budget on a reasoning-capable Flash
  model can still spend time thinking that a capped budget would skip.

## What other systems do, ranked by expected payoff here

**1. Stream the answer instead of waiting for it whole.**
Not a latency fix -- a perceived-latency fix, and the literature is
unanimous that it is the single biggest lever: streaming cuts perceived
wait from 5-15s to under 500ms, and users rate streamed output ~40% faster
than buffered output at identical wall-clock time. We already stream
*progress steps* (`research_with_progress`); we do not stream the *answer
text* itself -- the reader watches "Assembling the answer" and then the
whole thing appears at once. Streaming the draft's prose as it generates
closes that last gap. Cheapest change on this list, and it improves how
130s *feels* even before anything gets faster.
[Latency Perception Gap](https://tianpan.co/blog/2026/04/20/latency-perception-gap-ai-interfaces) ·
[Streaming LLM Responses](https://dev.to/pockit_tools/the-complete-guide-to-streaming-llm-responses-in-web-applications-from-sse-to-real-time-ui-3534)

**2. Parallelize the verification-loop's re-research, not just claims.**
Parallel fact-checking pipelines report 10 claims verified in 3-5s versus
30s+ sequential -- concurrency inside the window of one call rather than
paying for each claim in turn. Our own verification is already one batched
model call (`pipeline.py`: "one batched model call... for whatever stages
1-3 could not [resolve deterministically]"), so this lever is already
mostly taken on the *checking* side. Where it is not taken: when
`needs_research` sends the graph back to `research`, that second pass
re-runs the *same* angles from scratch rather than only the ones the
verifier flagged. Narrowing the re-research to the flagged claims (already
named as a known gap in `build.py`'s docstring: *"nodes.research() never
receives unsupported_claims"*) would shrink the loop-back itself, which is
the actual 45-60s cost.
[Parallel Fact-Checking](https://parallel.ai/blog/cerebras-fact-checker) ·
[VERDI single-call verification](https://arxiv.org/pdf/2605.11334)

**3. Set an explicit, small thinking budget on the Flash calls.**
Gemini's Flash-Lite tier is measured at sub-second responses when its
reasoning budget is controlled; an uncapped budget on a reasoning-capable
model can spend visible time on planning and drafting calls that do not
need deep reasoning -- ours is short-form JSON planning and templated
prose, not multi-step proof. This is a one-line-per-call config change and
worth measuring before anything structural.
[Gemini 2.5 Flash-Lite](https://developers.googleblog.com/en/gemini-25-flash-lite-is-now-stable-and-generally-available/)

**4. Prompt caching on the parts of every call that repeat.**
Every research/analyst/verification call re-sends the same instructions
and, within one thread, the same growing history. Reported gains are large
(41-80% cost, 13-31% faster time-to-first-token, "more than 2x" in some
provider benchmarks) and the mechanism suits our shape exactly: place the
static system instructions first and the per-turn question last, so the
prefix is byte-identical across calls in the same thread. Gemini's API
supports this today; nothing in `llm/client.py` currently marks a cache
boundary.
[Prompt Caching Guide](https://introl.com/blog/prompt-caching-infrastructure-llm-cost-latency-reduction-guide-2025) ·
[Vellum: Prompt Caching](https://www.vellum.ai/llm-parameters/prompt-caching)

**5. Parallelize the angle loop when more than one angle is planned.**
Directly matches the sequential loop named above. Multi-agent search
literature reports 5-20x on the *search* step specifically when angles run
concurrently instead of one after another. Since most questions already
plan one angle (by design -- `research_plan.py` prefers ONE), this only
pays off on the minority of questions that plan 2-3, but for those it is a
clean win with no accuracy trade-off, since the angles are independent
searches by construction.
[Parallel LLM Agents](https://arxiv.org/pdf/2507.08944)

**6. Semantic cache for repeated or near-duplicate questions.**
Cache hits reported at 2-4x faster, "50-100x" in the best case, because a
hit skips the model call entirely. Lower priority for a legal research
tool specifically: two lawyers rarely ask the *same* question, and a wrong
cache hit on a legal answer is a worse failure than a slow one. Worth doing
only for the intent-classification layer (greeting/thanks/pleasantry are
already a zero-cost regex, so this would apply to the *planner's*
legal-vs-not judgment on borderline phrasing) rather than for full answers.
[Semantic Caching Guide](https://redis.io/blog/what-is-semantic-caching/)

**7. Route by task complexity, not just by a fixed model chain.**
Model routers report handling 70-80% of subtasks on small/fast models at
5-10x lower cost, reserving a stronger model only for what needs it. We
already do a coarse version of this -- `case_model_chain` vs `model_chain`,
and the deterministic gates in CLAUDE.md's §4 ("deterministic before
model") skip a call entirely for lookups a regex can settle. The remaining
opportunity is inside the graph: `context_builder`, `clarification` and
`draft` may not all need the same model tier as `analyst`, which is doing
the actual legal reasoning. Worth measuring per-node latency before
touching this -- see "What to measure first" below.
[Model Routing Overview](https://learn.microsoft.com/en-us/azure/foundry/openai/concepts/model-router-how-it-works)

## What Harvey and Perplexity do differently

Useful context, not directly portable. Harvey uses LanceDB/PGVector RAG
much like we do, with heavy legal fine-tuning rather than a latency trick.
Perplexity's legal product routes each subtask to a *different provider*
picked for that subtask's shape (deep retrieval to one model, drafting to
another, short/fast requests to a fourth) and assembles the pieces --
closer to idea 7 above, but across vendors rather than within one chain.
Neither publishes a number comparable to our 30-130s figure, so this section
is architecture-for-ideas, not a benchmark to match.
[Harvey RAG Architecture](https://www.harvey.ai/blog/enterprise-grade-rag-systems) ·
[Perplexity Legal Platform](https://www.techtimes.com/articles/319208/20260627/perplexity-launches-legal-ai-platform-20-model-agent-targets-law-firm-workflows-above-westlaw.htm)

## What to measure first

Every idea above is a guess at *where* the 130s goes until it is measured
per node. `CLAUDE.md`'s own rule (§1: state assumptions, don't guess) argues
for adding per-node timing to the graph stream event before picking which
of 1-7 to spend time on -- the loop-back (#2) and the angle count (#5) only
matter on the subset of turns that hit them, and right now nothing records
which subset that is.

## Ranked by effort-to-payoff

| # | Change | Effort | Payoff | Risk |
|---|---|---|---|---|
| 1 | Stream the answer text | Small | Large (perceived) | None |
| 3 | Cap thinking budget | Small | Unmeasured, likely worthwhile | Low -- reversible |
| 4 | Prompt caching | Small-Medium | Medium-Large | Low |
| 2 | Narrow re-research to flagged claims | Medium | Large, only on Verified | Low -- already a named gap |
| 5 | Parallelize multi-angle search | Medium | Medium, only on 2-3 angle questions | Low |
| 6 | Semantic cache (planner only) | Medium | Small | Medium -- cache-correctness for a legal tool |
| 7 | Finer-grained model routing per node | Large | Unmeasured | Medium -- needs per-node data first |
