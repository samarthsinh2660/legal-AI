# Where a turn's time goes, 2026-09-06

Measured against the containerised stack with real model calls, by reading
the timestamps already in `run_events` — each step event is stamped, so the
gap between two of them is the node that produced the later one. No
instrumentation was added.

## The turn that started it

    POST returned in                                21ms
    answered in                                    108.4s

    Understanding the question                       1.3s
    Checking what is missing                         0.0s
    Searching statutes and judgments               104.0s   <- 96%
    Drafting the analysis                            1.7s
    Checking every claim against its source          0.1s
    Assembling the answer                            0.1s

One node, 96% of the wall clock. But the next two turns on the same worker
took **18.1s** and **40.2s**. So most of that 104s was not the work — it was
the first time the process did anything.

## What the 104 seconds actually was

From the worker's own log across that window:

| | |
|---|---|
| 10 × `429 Too Many Requests`, six models, 22:46:46 → 22:47:31 | **45s** |
| 69 HTTP round-trips to huggingface.co, 22:47:42 → 22:48:03 | **21s** |
| the model load itself, and the real retrieval and reasoning | the rest |

**66 of 108 seconds was neither retrieval nor reasoning.**

### The 69 requests were revalidation, not download

The weights are already in the mounted volume — 547 MB of it. Every one of
those calls was a HEAD asking whether a file that cannot change had
changed. Measured directly:

    model load, revalidating against huggingface.co    27.3s
    model load, cache only (HF_HUB_OFFLINE=1)           6.6s

Both models are `lru_cache`d, so this is once per process. That is what
made it invisible: the second question is fast, so nobody looks at the
first.

### The 45 seconds was the backoff, paid six times

A 429 is two different failures wearing one code — a per-minute limit that
clears in seconds, or a daily cap that does not. The client backs off once
to tell them apart, which is right. It was doing it **per model**: six
models × one 8-second sleep = 48s to learn what the first sleep already
said.

## The two fixes

**1. Load the models before the worker says it is ready.**
`Worker.warm()` runs before the first claim. A failure is logged, not
raised — a model host that is down should cost the research path, which
fails on its own terms, not a worker that can still draft documents and
answer from a thread.

**2. Pay the 429 backoff once per call, not once per model.**
If eight seconds did not clear the limit for the first model, eight more
will not clear it for the second.

## After

    first question after a cold start    108.4s  ->  32.1s
    second question                       18.1s  ->  18.1s

The 26s of model loading still happens. It is now paid at container start
rather than inside somebody's turn:

    worker.loop  models loaded in 26.0s
    worker.loop  worker ready, serving research, draft

To be exact about who still waits: a question asked *during* those 26
seconds queues until the worker is ready, so it is slow too — but its run
row says `queued`, and the screen says the honest thing rather than showing
a turn that looks stuck mid-research. Every question after that pays
nothing. Before the change, each worker's first question paid the whole
26s inside the answer.

## Confirmed after the change

Both QA suites re-run clean against the rebuilt worker: 41/41 over HTTP,
8/8 on process failures. The backend suite is 1231 and the frontend 144.

## What is left, and what it would cost

- **`HF_HUB_OFFLINE=1` would take the 26s startup to 6s.** Not shipped: it
  is now startup time rather than a reader's time, and with an empty cache
  offline mode fails outright (`OSError: couldn't connect ... and couldn't
  find them in the cached files`) — a bad default for a first deploy. The
  alternative, baking the weights into the image, costs ~550 MB on an image
  that was just cut from 5.77 GB.
- **The steady-state 18–40s is two model calls**, and nothing here touches
  that. It is the planner plus the analyst, on a free-tier key.
- **The free-tier quota, not the queue, is what caps throughput.** Three
  workers took 62 rate-limited responses between them in 45 minutes.
