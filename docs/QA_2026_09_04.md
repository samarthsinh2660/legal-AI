Manual pass against `https://legal-ai-swart-one.vercel.app` (frontend) and

## 1. CRITICAL — a date-dependent clarification can never be answered

**What happens.** Ask anything the app recognises as turning on a
limitation period ("limitation", "time-barred", "condonation", "how long
do I have", "delay in filing"), and it correctly asks *"When did this
happen? The time limit that applies depends on when the cause of action
arose."* Answer it — with a plain date, with "the cause of action arose
on...", any phrasing — and it asks the **identical question again**. This
repeats forever; the thread cannot be advanced by any answer.

**Reproduced live**, thread `56545ff66134409e87a9fe4e42ec471b`:

    Q:  What is the limitation period for filing a suit for recovery of money?
    A:  When did this happen? ...
    Q:  The debt was due on 1 January 2022 and has not been repaid.
    A:  When did this happen? ...            <- identical, unchanged
    Q:  The cause of action arose on 1 January 2022.
    A:  When did this happen? ...            <- identical, third time

**Root cause**, found by reading the code, not guessed:
`legal_ai/context/models.py` declares `ThreadContext.relevant_date_from:
date | None = None`. `legal_ai/context/clarification.py` reads it to decide
whether to ask again. **Nothing in the codebase ever assigns it** — grepped
the whole tree; the only occurrences are the one declaration, the one read
in the gate, and two more reads that pass it downstream as a filter. There
is no date parser, no extraction step, no writer at all. The field is
permanently `None`, so the gate's `not context.relevant_date_from` is
permanently `True`, so the question is permanently unanswerable.

**Confirmed isolated to this one field.** The sibling gate — "Which state
is this in?" for RERA/rent/stamp-duty questions — resolves correctly on
the first answer (`jurisdiction.state` in `context/builder.py:59` *is*
populated, by matching the rewritten question against a state-name list).
Reproduced live, thread `744499ac1eaa40429f9227065ae2c582`: answered
"The project is in Maharashtra." once, and research proceeded immediately.
So this is not a broken clarification *system* — it is one specific dead
field, and every date-dependent question hits it.

**Impact.** Any real limitation-period question — a common, everyday
question for exactly the lay users this product also serves — is a
dead end today. Not degraded, not slower: unanswerable, with no error and
no way out except starting a new thread and avoiding the trigger words.

**Fix shape** (not implemented — this was a QA pass, no code changed):
`context_builder` needs a date-extraction step, matching what
`_STATE_DEPENDENT` already does for state, writing into
`ThreadContext.relevant_date_from` from either the question text or a
structured slot-filling turn. Small, contained fix once someone opens
`context/builder.py`; the regex infrastructure for the parallel state case
is already there as the template.

## 2. Positive finding — verification caught a real gap, live

Verified-mode run on *"What penalty applies if a promoter fails to
register a project under RERA?"* rendered a lede citing RERA s.59 (10%
penalty; continued violation -> up to 3 years' imprisonment, a further 10%
fine, or both) — correct against the actual Act — **and** a red "Evidence
against this" box: *"What we retrieved does not support the claim,"*
naming a specific retrieved passage that didn't back a specific assertion.

This is the three-state honesty pattern (CLAUDE.md #2) doing its job in a
real production run, not a controlled test: the system found evidence
against its own draft and surfaced it rather than smoothing over it.

## 3. Positive finding — source links are now correct (from the earlier fix)

Same RERA answer: two statute citations rendered as real, clickable India
Code links; four Supreme Court judgments correctly said *"We hold no
public page for this one — opens in the citation graph"* rather than
claiming a link that doesn't exist. One live-discovered judgment (outside
the pre-ingested corpus) carried its own real external link, distinct from
the corpus copy of the same case — confirms the discovery path and the
corpus path are both wired correctly end to end.

## 4. Positive finding — the interrupted-turn fix holds under a real refresh

Refreshed the browser mid-research on a live thread (not a unit test — an
actual page reload against the deployed server). The question survived;
the thread reopened with it intact rather than showing an empty pane. This
is the fix from the previous session, confirmed working against production
rather than only against the test suite.

## 5. Minor — one long-running turn produced a stuck-looking "Starting research…"

On the second/third turn in an existing thread, the progress pane sat on
the generic "Starting research…" placeholder for 30+ seconds with zero
step events, long enough to look hung. Checked directly rather than
assumed: the network request was genuinely still `pending`, and the server
log showed no second completion yet — so this was real latency, not a
frontend bug. Once the first step event landed, the rest of the run
progressed and rendered normally. Consistent with `docs/SPEED_2026_09_03.md`'s
finding that `context_builder`/`clarification` can be slow before their own
step fires. Not a defect on its own, but a reminder that the "Starting
research…" label gives no signal of how long a genuinely slow first step
will take — worth keeping in mind if #1's fix adds a model call to that
same early stage.
