# QA pass and fixes — 1 September 2026

What was broken, what the research said, what changed, and what is still open.
Every number here is measured against the running stack, not estimated.

---

## 1. Where it started

Fifteen research runs as a lawyer would drive them. Five timed out at 300s,
no verified-mode question ever finished, and a greeting cost 65 seconds.

```
"hi"                     65s   full research pipeline, then "that is a greeting"
"thanks!"                80s   answered with the law on GRATUITY
"what can you do?"      176s   answered on s.151 CPC inherent powers
s.138 verified          300s   TIMEOUT
s.138 quick              96s   answered, but omitted every filing requirement
case-seeded question      -    "Which state is this in?" for a Maharashtra case
follow-up question        -    replayed the previous answer verbatim
```

What already worked, and still does: **zero fabricated citations** (8/8 ids
resolved to real, on-topic documents), honest refusal on out-of-corpus
questions, follow-up referent resolution, airtight tenant isolation.

## 2. What the research said

Fifteen searches, on how systems like this are actually built rather than on
prompt wording alone.

**Intent classification comes before retrieval.** Production RAG chatbots
classify the message first and only route knowledge-seeking queries into the
pipeline; greetings and acknowledgements are answered directly. Every
production chatbot keeps a deterministic NLP layer under the LLM, because an
intent classifier either matches or does not, whereas an LLM outputs prose
that can be wrong.

**Give the model an escape hatch.** Hallucination is a system-design
problem: if you do not define what happens when the input is out of scope,
the model invents an answer. Define an explicit output path for "I cannot",
and never force an answer through a rigid output contract.

**Retrieve the parent, not the chunk.** For statutes, chunk only within a
section, and fetch the *full section* associated with a matched chunk before
inference. Minimal chunking suits structured text; hierarchical chunking is
for case law.

**Circuit-break a failing model.** Retrying an unhealthy provider on every
request before falling back only adds latency. Skip it for a cooldown, then
let one request probe it.

**What the leaders do.** Harvey and CoCounsel both ground every claim in
retrieved content, expose the reasoning step by step, and — the important
one — *flag any citation they cannot verify rather than including it*.
Harvey reports 99.7% verified citation accuracy. The Stanford HAI study
found the major legal tools still hallucinate 17–19% of the time, and that
**poor retrieval is what triggers legal hallucination**. Citation
hallucinations are called "even more pernicious" than invented cases.

Our four-verdict architecture already matches that guidance. The gaps were
execution, not design.

## 3. What was fixed

### 3.1 Verified mode never finished — a datable regression

Commit `fe00eee` (28 Aug) widened the re-research trigger from `UNSUPPORTED`
to *every* non-SUPPORTED verdict. The verifier's own prompt says "prefer the
more cautious verdict", so a single `PARTIALLY_SUPPORTED` sent the whole run
back through research and analysis: 4 model calls became 8, at 45–60s each.

`VerificationReport.needs_research` now admits only the `reference` stage —
a missing document is the one defect another search can close. A misgrounded
paraphrase or an invented quote is a defect in the *claim*, and the second
pass repeats the same searches.

Corpus growth was **ruled out by measurement**: retrieval is ~0.1s of SQL
plus a fixed 50-candidate rerank that does not grow with the corpus.

### 3.2 A discarded model call

`research()` summarised its own evidence and nothing ever read the result —
60.3s of a 233s turn. Removed from the graph path; `summarise()` remains for
a caller that wants prose.

### 3.3 Two dead models re-probed on every call

Two Gemini endpoints at the head of the chain were returning 503, and every
`generate()` walked both — roughly 40s of fallthrough per call. Added a
circuit breaker: a model that fails is skipped for 180s, a success clears
it, and if the whole chain is cooling down it is tried anyway. Failing fast
must never become refusing to try.

### 3.4 A case file did not reach the thread

`start_session` seeded findings and description but never jurisdiction, so a
matter recorded as *Maharashtra RERA* produced a thread with no state and
the clarification gate stopped to ask — a question the user answered when
they created the case. The New Case form did not collect `state` either.
Both fixed; the question still wins over the case, so a Karnataka question
inside a Maharashtra matter stays a Karnataka question.

### 3.5 Follow-ups replayed the previous answer

`answer_from_history` was a stub returning the last assistant turn's text.
It now composes a real answer from the thread's stored claims. The model
selects claims **by number**, so an evidence id is not representable on that
path — fabrication is impossible, not merely validated away. A claim can
move *down* the four verdict buckets, never up. Where the thread cannot
answer, it says so instead of replaying.

### 3.6 Small talk went through the full research graph

Two layers, as the research recommends.

- **Deterministic gate** (`conversation/intent.py`): greetings, thanks and
  capability questions answered with **zero model calls**. Patterns match
  the whole message, so `"hi, can I claim a refund?"` still researches.
- **Escape hatch in the planner prompt**: the planner may now return `[]`
  for a message with no legal issue, kept distinct from a garbled reply
  (which still falls back to searching, so a real question is never
  dropped). This catches what the patterns were never told about.

The root cause was the prompt's output contract: *"Return ONLY a JSON array
of angles"* left no way to decline, so `thanks!` became a search for
gratuity.

### 3.7 Statute sections reached the analyst truncated

**The most consequential fix.** Retrieval carried the single nearest chunk.
19% of the 35,601 sections we hold span more than one chunk, and s.138 NI
Act is the case that exposed it: the offence is in chunk 1, the provisos
that decide whether a complaint is valid are in chunk 2.

Answers therefore described the offence and omitted the presentation
window, the **thirty-day demand notice** and the **fifteen-day payment
window**. A junior relying on that files late.

Sections up to 4,000 characters (the 95th percentile is 3,114) are now
carried whole, provisos included; longer ones still fall back to the
passage, and judgments are untouched.

```
before   5 claims, no filing requirements
after    7 claims, including presentation window, 30-day notice, 15-day window
```

### 3.8 The corpus does not hold the IPC — and never said so

The Indian Penal Code, the Code of Criminal Procedure and the Indian
Evidence Act are **absent**. Their 2023 replacements — Bharatiya Nyaya
Sanhita, Nagarik Suraksha Sanhita, Sakshya Adhiniyam — are present.

This matters more than it looks: an offence committed **before 1 July 2024
is still charged under the old code**, so a lawyer asking about IPC s.498A
is asking a live question. Search answered it with unrelated near-misses.

Answers naming a repealed code now carry a coverage note saying what is not
held, what replaced it, and that the older code still governs earlier
offences. It is a statement about our shelf, not about the law — the same
category as `support_not_checked`.

### 3.9 An unreadable model reply produced a blank answer

The exception path said "analysis was unavailable"; an *unparseable* reply
returned `{}` and rendered as an empty answer, indistinguishable from "the
corpus holds nothing". Both now say the same thing.

## 4. Where it is now

```
"hi"                          0s   (was 65s)
"thanks!"                     0s   (was 80s + gratuity law)
"what can you do?"            0s   (was 176s + s.151 CPC)
"write me a poem"            28s   "I only research Indian law" — no disclaimer
s.138 complaint, quick      100s   7 claims incl. all three filing requirements
s.138, verified             224s   (was 300s TIMEOUT)
RERA refund, verified       146s   (was 300s TIMEOUT)
case-seeded question        146s   no clarification — state inherited
s.498A IPC                   69s   coverage note fired
```

**Tests:** 688 backend, 79 frontend. The two guarantees that matter most —
verdict buckets never merging, and SSE frames spanning chunk boundaries —
are mutation-tested: introduce the defect and the tests fail.

## 4b. Ranking — fixed 2 September

A DB backup was taken first (`backups/20260902/`, verified with
`pg_restore -l`).

### Section titles were never embedded

`search_vector` is generated from `title || full_text`, so keyword search
always covered titles. The vector index never did. Measured: **93% of
sections (29,945 of 32,163) had no part of their title in any chunk.** The
section titled *"Dishonour of cheque for insufficiency, etc., of funds"*
could not be retrieved by that phrase.

`chunk_and_store` now embeds `title + text` while storing `text` unchanged,
so the vector is title-aware and the passage shown to the model is not
padded. `scripts/reembed_titles.py` backfilled 17,739 existing section
chunks in 489s.

    "dishonour of cheque for insufficiency of funds"   MISS -> rank 4

Judgments were left alone: 345,761 chunks against 17,867 is 20 hours
against one, and a case name is usually already in the body.

### The reader's words and the statutory rewrite find different things

The planner rewrites a question into statutory vocabulary before searching
("builder did not hand over my flat" -> "promoter fails to give
possession"). Measured over `evals/datasets/retrieval.json`, rewriting
*alone* is a trade, not a win — it rescued three questions that missed and
broke eight that worked, because it discards the reader's own wording.

Searching both and fusing by rank is a clear net win, though not a
uniform one -- per question, against the raw baseline:

    20 better    7 worse    23 unchanged

Authoritative, from the committed harness over all 50 questions
(`python -m evals.run` and `--fused`):

                MRR    r@1   r@5   r@10
    raw        0.333   18%   56%   68%
    fused      0.404   22%   68%   72%

A throwaway script during development reported 0.469 for the fused path.
It is not reproducible from the committed harness and is recorded here only
so nobody chases it: the number to cite is 0.404. Phase 7 lost time to
exactly this once before, with an uncommitted 0.530.

The per-question breakdown below comes from that development script, so
treat its shape as indicative and its absolute ranks as approximate:

                MRR    r@1   r@5   r@10
    raw        0.311   16%   54%   68%
    rewritten  0.350   18%   58%   70%
    fused      0.469   36%   64%   70%

The shape matters more than the tally. Five of the wins are a MISS
becoming a hit (arbitration-agreement, wrongful-restraint,
restraint-of-trade, hurt-dangerous-weapon, rera-promoter-duties) and eight
more reach rank 1. All seven losses were already marginal, sitting at ranks
7-9, and four of them slipped just past the cut:

    rape-certain-cases              8 -> MISS
    state-consumer-commission       8 -> MISS
    food-misleading-advertisement   7 -> MISS
    adoption-jj                     9 -> MISS

Recall@10 still rose, so more entered the top ten than left it.

On the unfused path the committed harness measures, the title fix alone
moved MRR 0.326 -> 0.333. No regression there either.

In situ through `supervisor.research`, on the first 11 questions:

                            MRR    r@1   r@5   r@10
    raw (question only)    0.515   27%   73%    82%
    fused (shipped path)   0.523   18%   91%   100%

`hybrid_search` takes an `also` phrasing and fuses the two orderings;
`supervisor` passes the reader's question alongside each statutory angle.
It costs a second retrieval — about 4s on a turn that already takes 100.

`evals/run.py --fused` measures this path. Without that flag the harness
measures raw retrieval, which the product no longer uses.

Not fixed: `"cheque bounce"` still misses s.138. "Bounce" appears nowhere
in the Act, and no rewrite the planner produced recovered it.

## 4c. Model calls per turn

Measured 2026-09-02 by counting `llm.client.generate` calls through the
compiled graph.

    first question, quick        2 calls    22,463 prompt chars
    first question, verified     3 calls    68,235 prompt chars
    follow-up adds               2 calls     1,510 prompt chars
                                 (rewrite the question, route it)

So a turn costs 2 to 5 calls. `summarise` was 1 of those and bought
nothing; verification is one batched call, not one per claim. Verified mode
costs a third call and triples the prompt, because the evidence is sent
again to be checked against.

For scale: the industry write-ups put agentic workflows at 10-20 model
calls per task. Nothing here is close to that, and the fusion added a
retrieval, not a call.

## 4d. Corpus and links — 2 September

Backup taken and verified first: `backups/20260902-1819/`.

### IPC and CrPC ingested

India Code does not have them as structured sections -- verified twice
against the live REST API, which returns only BNS 2023 sections for
"Punishment for murder" and only IPC *amendment* Acts by title. They came
instead from `civictech-India/Indian-Law-Penal-Code-Json`, cross-validated
against devgan.in: both list 575 IPC sections and agree on every one.

    IPC 1860    574 sections   act:ipc-1860
    CrPC 1973   525 sections   act:crpc-1973

`source_type` is `"research"`, the Indian Kanoon tier -- a community
compilation must not be labelled a government source. Neo4j has both Acts
with `CONTAINS` edges (574 / 525). No section is unretrievable: every one
has a document embedding or chunks.

**IPC s.304B (dowry death) is missing.** Its body is empty in the source
and it was skipped rather than stored as an empty row, which would read as
coverage we do not have. It needs a body from elsewhere.

`retrieval/coverage.py` no longer claims we lack these codes. The Evidence
Act is still absent and still reported.

### The eval regressed, and most of it is the dataset

    before IPC/CrPC   MRR 0.404   r@1 22%   r@5 68%   r@10 72%
    after             MRR 0.321   r@1 14%   r@5 62%   r@10 66%

The dataset expects the 2023 code. Now that the codes it replaced are held,
their twin sections compete for the same slot: `murder-punishment` expects
BNS s.103, and IPC s.302 "Punishment for murder" takes rank 1 while BNS
s.103 sits at 3. **Both are correct** -- IPC governs any offence before
1 July 2024.

Re-scored in one harness, accepting either code's version of the same
provision:

    expected id only        MRR 0.278   r@5 46%
    or the same provision   MRR 0.329   r@5 52%

**Fixed the same day.** 17 criminal questions now accept either code's
version of the provision -- 14 paired by section title, 3 by hand where the
titles diverge (BNS 118 covers IPC 324 and 326; BNS 86 "Cruelty defined"
is IPC 498A; BNS 65 is IPC 376). Re-measured:

    before IPC/CrPC   old dataset    MRR 0.404   r@1 22%   r@10 72%
    after IPC/CrPC    old dataset    MRR 0.321   r@1 14%   r@10 66%
    after IPC/CrPC    fixed dataset  MRR 0.395   r@1 24%   r@10 72%

So the drop was the instrument, not the corpus. Adding 1,099 sections left
MRR within noise of where it was and moved recall@1 up from 22% to 24%.
The lesson is the one the dataset now encodes: a benchmark that assumes one
right answer breaks the moment the corpus honestly holds two.

### India Code URLs repaired

The site moved and renumbered every handle, so all 35,601 stored statute
URLs 404'd and no citation was clickable.

    832 / 860 Acts resolved
    34,940 sections now on live indiacode.gov.in handles
    676 rows left on the dead host -- 28 Acts with no exact title match

Mapped by sweeping every central SECTION item and matching on
`(act_id, section_number)`; the sweep is verifiable, collecting 35,359 of
the 35,359 handles the index reports. Unmatched Acts were left alone rather
than fuzzy-matched -- our `Tribunals Reforms Act, 2021` sits next to the
site's `Tribunals Reforms Act, 2026`, a different Act.

Spot-checked through `server/api/pid/find`, which gives 302 for a real
handle and 404 for a bogus one, because the site is an SPA that returns 200
for any path. 8 of 8 random repairs resolved; the bogus control 404'd.

`_DEAD_HOSTS` stays: the check is per row, so the 34,940 repaired rows are
offered and the 676 unrepaired ones are still withheld.

The JSON file the IPC came from is now withheld the same way a judgment
year-tar is -- it holds all 575 sections, so it does not open the provision
a reader clicked.

## 5. Still open

**`/search` does not fuse.** The chat path now searches the reader's words
and the statutory rewrite together; `/search` still passes the raw phrase
straight to hybrid retrieval, so it is measurably worse than chat on the
same corpus. Wiring the same fusion in costs a model call per search.

**Judgment chunks are not title-aware.** Only sections were backfilled.

**Corpus coverage.** No IPC, CrPC or Evidence Act; state RERA rules and High
Court decisions are largely absent. The system now says so when asked
directly about a repealed code, but not for a state-rules question.

**Cancellation.** A client that disconnects mid-research leaves the run
going. Needs a job queue.

**Nothing has been verified in a browser.** The Chrome extension has never
connected in this environment (`list_connected_browsers` returns empty), so
the provenance badges, evidence blocks, graph hover-dim and drag, confirm
dialogs and every focus state are unverified by eye.

**No landing page.** An unauthenticated visitor lands on the login screen
with no explanation of what the product is.

## 6. Release view

Safe for a lawyer to use **with the standing caveat the product already
states**: it answers from a partial corpus and marks what it could not
check. The defects that made it unsafe — answers missing the requirements
that decide a case, a silent replay of an earlier answer, silent absence of
the IPC — are fixed.

Not yet safe to leave unattended on criminal matters, where the corpus gap
is largest.
